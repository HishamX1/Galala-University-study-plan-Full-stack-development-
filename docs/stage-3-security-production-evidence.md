## Dependency-remediation investigation (read-only; no change approved)

The fresh audit JSON contains two moderate package entries for one advisory: direct `exceljs@4.4.0` is marked through its vulnerable dependency, and the transitive `uuid@8.3.2` node is the advisory target. The advisory concerns out-of-bounds writes from UUID v3/v5/v6 only when a caller supplies an output buffer/offset. The inspected ExcelJS package uses CommonJS `require('uuid')`, destructures only `v4`, and invokes it without arguments. This reachability review narrows the currently observed path, but does not make the npm finding disappear or prove safety for all ExcelJS behavior/future releases.

The root `package.json` currently has no `overrides`. The npm registry and current [upstream ExcelJS manifest](https://github.com/exceljs/exceljs/blob/master/package.json) still show `exceljs@4.4.0` as latest with `uuid@^8.3.0`; no patched UUID version satisfies that declared range. UUID `11.1.1` is the lowest patched release and retains a Node CommonJS export; UUID 12 removed CommonJS support. npm's reported forced repair, `exceljs@3.4.0`, would be a major-version downgrade and is not recommended for this XLSX import/export application.

**Recommendation:** do not change PR #7 dependencies. If remediation is authorized before ExcelJS updates its dependency range, test only a narrowly scoped candidate override of `uuid` beneath `exceljs@4.4.0` to exact `11.1.1` on a separate feature branch. The proposed npm shape is `"overrides": { "exceljs@4.4.0": { "uuid": "11.1.1" } }` (npm's [nested override mechanism](https://docs.npmjs.com/cli/configuring-npm/package-json/#overrides)). This deliberately crosses ExcelJS's declared `^8.3.0` range and is a candidate, not a compatibility or safety claim. Prefer an official ExcelJS release that declares a patched compatible UUID dependency when available.

Before approving that candidate, require: (1) clean isolated `npm ci`, `npm ls exceljs uuid`, and a new production audit proving no vulnerable UUID remains; (2) a runtime compatibility check resolving UUID from ExcelJS itself and generating/round-tripping conditional-formatting workbook identifiers; (3) XLSX export/import and backup round-trip tests covering current catalog fields, UTF-8/text/date/numeric values, empty and multi-sheet workbooks; (4) preservation of the existing parser security cases (formula, hyperlink/note, malformed ZIP, size/ratio/row/cell limits, worker concurrency/timeouts); (5) disposable-PostgreSQL staged XLSX publication and injected-failure rollback/audit/state-retention tests; and (6) the complete CI suite plus a fresh full audit with development dependencies included and residual findings documented. None of these candidate-override tests were run in this read-only investigation.

No dependencies were installed, upgraded, overridden, or removed. No production data, dashboard settings, migrations, or deployments were changed.
