# Backend HTTP response audit

Audit scope: the root `backend/src/` request pipeline, including `server.js`, `routes/catalogRoutes.js`, controllers, authentication, shared middleware, and response helpers. Routes are matched by centralized path/method checks rather than an external router registry. The duplicated `modernization/` tree is excluded by the repository contract.

## Response lifecycle findings

- The catalog controller used `json()` as its return value in matched mutation branches. The helper wrote and ended the response but returned `undefined`, which was interpreted as “not handled”; dispatch continued to the API 404 and raised `ERR_HTTP_HEADERS_SENT`. This is the reproduced defect’s source.
- The API catch could write a mapped error unconditionally after a controller had completed or partially committed a response. It now logs the original failure and avoids a second write; an incomplete committed response is destroyed.
- The async HTTP server callback had no outer rejection handler for errors outside `handleApi()`. It now has a shared fallback that writes one generic 500 before headers, or destroys an incomplete response after headers.
- `parseBody()` and awaited controller/service promises send malformed JSON, size-limit, stream, validation, authorization, database, and unexpected failures through the API catch. Auth and admin handlers similarly return their matched marker after each response.
- `json()` returns an explicit handled marker and both shared response helpers reject a duplicate write. The permission helper explicitly returns false after denial so a response marker cannot accidentally continue dispatch.
- Response writers found in root backend code are `json()`, `download()`, `writeUnexpectedError()`, and static-file `writeHead()`/`end()` in `server.js`. No Express-style `send`, `redirect`, or direct `write()` calls were found. No custom route timeout exists; email HTTP and XLSX worker timeouts are internal service behavior, not response lifecycle timeout coverage.

## Changes and local verification

- `json()` now returns `true`; permission denial explicitly returns `false`; duplicate writes are rejected by the shared response helpers.
- The API catch preserves errors in logs and never attempts a second response after headers are sent. The server async callback has a safe outer boundary and final request logging.
- `scripts/http-response-boundary-test.js` passed for successful async handling, database and unexpected rejections, validation failure, authorization, response-after-completion rejection, partial response termination, duplicate helper attempt, download, and unknown routes.
- `npm run check`, `npm run test:http-response-boundary`, `npm run test:db-guard`, `npm run test:admin-routes`, `npm run test:notification-read-contract`, and `npm run test:refresh-rollback` passed locally. Other database-free contract tests also passed during this audit (dashboard, session restoration, catalog cache/concurrency, complaint visibility, error disclosure, security, admin UI/operations, import security/routes, password recovery, and support pagination).
- `npm run test:http-response-postgres` was attempted locally and correctly stopped at `TEST_DATABASE_URL is required`; no database connection was attempted.
