# Persistent notification read state

Dashboard notification read state is stored per authenticated account in `public.notification_read_states`. A record is keyed by the user, notification type, and source ID, so repeated or concurrent marks are idempotent and one user's action does not change another user's state. Removing an account cascades its read-state records. The API verifies ownership for `communication_outbox` entries and limits reset-request, complaint, and backup alerts to the super-administrator dashboard; unauthorized or missing items return the same not-found response.

`POST /api/notifications/read` accepts `{ "notificationKey": "<type>:<source-id>" }`. `POST /api/notifications/read-all` marks unread notifications currently shown on that dashboard as read. The latter is deliberately scoped to the displayed list (currently at most ten items), not older notifications that the dashboard has not loaded. The existing dashboard response retains each notification's `id` and `read` fields and adds `notification_key` for the mark-read request. The badge counts unread entries in that displayed list.

The frontend waits for a successful API response before changing an unread item or its count. Failures keep the notification unread in the current view and display an error. A later dashboard request reads the persisted state, so it survives refresh and sign-out/sign-in.

Migration `20261022150000_notification_read_states.sql` adds the state table and enables row-level security, matching the existing backend-owned PostgreSQL access pattern. The backend is the only client of these endpoints; browser code never accesses the database. The disposable PostgreSQL integration test verifies account ownership, super-admin-only synthetic alerts, duplicate/concurrent updates, mark-all, and persistence across dashboard reads. Apply the migration through the approved database migration procedure before deploying this feature; this implementation does not apply any hosted migration.
